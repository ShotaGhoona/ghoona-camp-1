# レポート作成ガイドライン

## 概要

本ディレクトリは、開発作業の成果物をレポート形式でまとめるための指南書です。統一されたフォーマットで技術資料を作成することで、チーム内での知識共有と引き継ぎを効率化することを目的としています。

## レポート作成の基本方針

### 1. 文書構造の統一
すべてのレポートは以下の構造に従ってください：
- **リビジョン履歴表**：必ず冒頭に配置
- **概要**：目的と対象範囲を明記
- **詳細内容**：実装内容や仕様を体系的に整理
- **共通パターン・ガイドライン**：再利用可能な知見
- **備考・注意事項**：今後の開発で注意すべき点

### 2. リビジョン管理の重要性
各レポートには必ずリビジョン管理表を設置し、以下のルールに従ってください：
- バージョンはセマンティックバージョニング（v1.0, v1.1, v2.0）
- 変更内容は簡潔かつ具体的に記述
- 日付はYYYY-MM-DD形式で統一

### 3. 対象読者の明確化
レポートを読む人（新規開発者、既存メンバー、外部協力者等）を意識し、適切な詳細レベルで記述してください。

## ファイル配置とネーミング規則

### ディレクトリ構造
```
docs/tasks/report/
├── README.md (本ガイドライン)
├── {分野}/
│   ├── {レポート名}.md
│   └── {レポート名}-{サブカテゴリ}.md
└── assets/ (必要に応じて画像等を配置)
```

### ディレクトリ分類
- **be-application/**: バックエンドアプリケーション関連
- **fe-application/**: フロントエンドアプリケーション関連  
- **infrastructure/**: インフラ・デプロイ関連
- **database/**: データベース設計・移行関連
- **api/**: API設計・仕様関連
- **security/**: セキュリティ・認証関連

### ファイル名規則
- **形式**: `{内容}-{種別}.md`
- **例**:
  - `dto-implementation-summary.md` (実装サマリー)
  - `api-authentication-analysis.md` (分析レポート)
  - `database-migration-guide.md` (手順書)
  - `error-handling-troubleshooting.md` (トラブルシューティング)

### 命名のガイドライン
- **ケバブケース**を使用（単語をハイフンで区切り）
- **英語**で命名（日本語ファイル名は避ける）
- **内容が分かりやすい**具体的な名称
- **種別**を末尾に含める（summary, analysis, guide, troubleshooting等）

## レポートの種類と作成指針

### 実装サマリー系レポート
- **目的**：実装された機能や仕様の全体像を把握
- **記載内容**：データ構造、API仕様、共通パターン
- **ファイル名例**：`dto-implementation-summary.md`, `component-structure-summary.md`

### 分析・検証系レポート
- **目的**：問題の特定や解決策の検討結果を共有
- **記載内容**：調査方法、発見事項、解決策
- **フォーマット**：課題→調査→結果→対策の流れ
- **ファイル名例**：`performance-bottleneck-analysis.md`, `security-vulnerability-analysis.md`

### 運用・保守系レポート
- **目的**：システムの運用知識や保守手順を文書化
- **記載内容**：手順書、トラブルシューティング、ベストプラクティス
- **ファイル名例**：`deployment-guide.md`, `backup-recovery-guide.md`

## 品質向上のための注意点

- **具体性**：抽象的な表現ではなく、具体的なコード例や手順を記載
- **網羅性**：関連する全ての情報を漏れなく整理
- **再現性**：他の開発者が同じ結果を得られるよう詳細に記述
- **保守性**：将来の変更に対応しやすい構造で文書化

このガイドラインに従うことで、チーム全体で一貫性のある高品質なレポートを作成し、効率的な知識共有を実現できます。
